API Architecture & Rate Limits

Guidelines for reliable client integrations, retries, and webhook verification.

1. Overview

All API endpoints are served over HTTPS and return JSON payloads with consistent error envelopes. Requests are authenticated using project-scoped bearer tokens.

Keep client integrations stateless where possible and prefer idempotency keys on mutating requests so transient network failures can be retried safely without duplicating side effects.

2. Authentication

Include your API key in the Authorization header on every request. Keys can be rotated in the dashboard with an overlapping grace window to prevent downtime.

Never embed secret keys in client-side bundles. Use short-lived session tokens when calling endpoints directly from browser contexts.

3. Rate Limits

Requests are metered using a sliding token bucket per workspace. Standard workspaces allow up to 120 requests per second with burst capacity for short spikes.

Inspect the X-RateLimit-Remaining and Retry-After headers to pace background jobs before hitting HTTP 429 responses.

4. Pagination

List endpoints use cursor-based pagination for stable ordering even when records are inserted or deleted between page fetches.

Pass the returned next_cursor parameter into subsequent requests until has_more evaluates to false.

5. Webhooks

Webhook deliveries are signed with an HMAC-SHA256 signature in the X-Signature header. Verify the raw request body using a constant-time comparison before processing events.

Acknowledge deliveries within 5 seconds with a 2xx status code and offload heavy downstream work to an asynchronous queue.

6. Error Handling

Client errors return 4xx status codes with a machine-readable code field and human-readable message. Server errors (5xx) should be retried with exponential backoff and jitter.

Log the X-Request-Id header on failed calls to speed up troubleshooting with support.
